# 06 · Pipeline spike results

**Date:** 2026-09-07
**Question:** does the Phase 2 build pipeline work headlessly the way [00-plan.md](00-plan.md) assumes, and what are the real numbers?
**Verdict:** yes, end to end. Bootstrap, compile and artifact production work from a Node script with no Arduino IDE, and a real Proffieboard V2.2 was backed up, flashed with the OS8 config and verified over serial (section 7).

Scripts: [`spike/run-spike.mjs`](../spike/run-spike.mjs) (build side, phases `bootstrap core proffieos compile errors dfu report`) and [`spike/flash.mjs`](../spike/flash.mjs) (install side, phases `detect probe backup flash restore`; writes require `SPIKE_CONFIRM_FLASH=1`). Raw data: `spike/results.json`, table: `spike/results.md`. Everything downloaded lives in `spike/.cache` (gitignored).

Machine: Intel i9-12900K (16 cores), 64 GB RAM, NVMe SSD, Windows 11. Expect laptops to be 2 to 3 times slower.

## 1. Bootstrap

| Step | Result |
|---|---|
| `arduino-cli` 1.3.1 Windows zip | Downloaded and extracted with one PowerShell call; runs with an isolated data dir via `ARDUINO_DIRECTORIES_*` env vars, no global install |
| `core install proffieboard:stm32l4` with the Proffieboard index URL | One command downloads core 4.6, xPack GCC 14.2.1 and the tools (dfu-util 0.9, dfu-suffix) |
| Downloads | 357 MB |
| On disk after install | **1.6 GB** (plan said ~1 GB; corrected) |
| ProffieOS v8.10 | Shallow git clone |

Takeaway: the toolchain manager is a thin wrapper around `arduino-cli`. It only needs to pin versions, verify checksums, and own the data directory.

## 2. Compile matrix

The "baseline" config is the stock `OS6_config_example.h` (Fett263 prop, edit mode, two blades: 136 px main + 6 px accent, five presets of real Fett263 library styles) with the board include swapped to V3 and the golden defines `SAVE_STATE` and `MOUNT_SD_SETTING` added. It is representative of what the app will generate.

| Build | Board | USB | Wall time | `.text` bytes | Flash used |
|---|---|---|---|---|---|
| baseline, first build | V3 | cdc_msc_webusb | 58.2 s | 227,560 | 45% of 507,904 |
| baseline, rebuild in a fresh build dir | V3 | cdc_msc_webusb | 63.6 s | 227,560 | 45% |
| baseline, rebuild reusing the build dir, no change | V3 | cdc_msc_webusb | 40.5 s | 227,560 | 45% |
| baseline, rebuild reusing the build dir, one colour edited | V3 | cdc_msc_webusb | 39.6 s | 228,088 | 45% |
| baseline, serial only | V3 | cdc | 57.6 s | 222,920 | 44% |
| baseline | V2 | cdc_msc_webusb | 54.3 s | 226,048 | **86% of 262,144** |
| stock OS6 example | V2 | cdc_msc_webusb | 49.0 s | 226,048 | 86% |
| stock V3 verification config (3 simple blades) | V3 | cdc_msc_webusb | 19.0 s | 197,328 | 39% |

Findings:

- **A realistic build is about one minute on a fast desktop.** The wait is dominated by compiling the single ProffieOS translation unit with its template-heavy styles; style complexity drives time (19 s for trivial styles, 50 to 60 s for five Fett263 styles). Plan for 1 to 3 minutes on user laptops and design the UI around an honest progress state.
- **Fresh build directories give no warm-build benefit.** Reusing the same build directory saves only 5 to 15 s. The only cache that matters is `sha256(config, OS version, FQBN) → .dfu`, as the plan already says. Keep one build directory per saber for the small saving.
- **Five rich styles already fill 86% of a V2 board.** The flash-budget meter is not optional. V3 has headroom (45%).
- **`Serial + WebUSB + Mass Storage` costs 4.6 KB over serial-only.** Cheap; keep the golden baseline.
- **Golden defines cost nothing measurable** on this config.

## 2b. OS8-native config with current Fett263 library styles

The OS6 example's styles predate the OS7/8 library, so a second config was built from styles generated by Fett263's ProffieOS7/8 Style Library (public access, "OS7.15 v3.44p") on 2026-09-07. The library gates its output behind a GPL/attribution acknowledgement, which the owner accepted; every style is reproduced in [`spike/configs/saberbench_v3_os8.h`](../spike/configs/saberbench_v3_os8.h) with its copyright header intact. Styles: Ahsoka Tano main blade, JuanSith Duality dual-phase blade, KyberPhonics Osha corruption blade (both dual-phase styles need `FETT263_SPECIAL_ABILITIES` and alt fonts on the SD card), and the Ahsoka crystal-chamber style for the 6 px accent strip. The config uses the golden defines plus `EXTRA_COLOR_BUFFER_SPACE 60` as the library recommends, and five presets, two of which reuse compiled styles with different argument strings.

| Build | Board | Wall time | `.text` bytes | Flash used |
|---|---|---|---|---|
| OS8 config, first build | V3 | 28.9 s | 216,304 | 43% |
| OS8 config, rebuild reusing the build dir | V3 | 23.8 s | 216,304 | 43% |
| OS8 config | V2 | 26.5 s | 214,792 | **82%** |

Findings:

- **Distinct style instantiations drive flash and compile time, not preset count.** Four distinct library styles (5 presets) cost 216 KB and 29 s; the OS6 example's ten instantiations (5 presets × 2 blades, all different) cost 227 KB and 55 s; three trivial styles cost 197 KB and 19 s. Presets that reuse a compiled style with a different argument string are free, exactly as the plan's "compile as little as possible" principle assumes.
- **The OS base with edit mode is the bulk of the image** (roughly 195 to 200 KB); each rich library style adds on the order of 2 to 5 KB on top. The flash meter should model a fixed base per feature set plus a per-distinct-style increment.
- **V2 is still at 82%** with only four rich styles. A V2 owner gets perhaps 10 to 15 distinct rich styles before hitting the wall; the meter must steer them toward argument reuse.
- **Style acquisition works as a user flow.** Driving the library, accepting its notice once, and pasting the generated code with its header is exactly what the app's "import a style" feature should support, and is the intended use under the library's GPL terms.

## 3. Artifacts

`arduino-cli` produces `ProffieOS.ino.dfu`, not `.bin`. It is the raw flash image (starts with the vector table) plus a 16-byte DFU suffix carrying VID `1209` PID `6668` and the `UFD` signature, added by `dfu-suffix` in the core's post-objcopy hook. `dfu-util -D` validates that suffix before writing. The core also writes `.iap` (the image without the 1 KB `.boot` section), `.elf` (9.5 MB, useful for size analysis) and `.map`. The upload recipe is exactly `stm32l4-upload.bat <vid> <pid> <file>.dfu`.

Implication: the flash engine hands the `.dfu` straight to `dfu-util`. Any future WebUSB path must strip the suffix.

## 4. Error scenarios

Every failure surfaced in **3 to 10 s**, because the config is included early and the compiler stops before the expensive codegen. Fast validation feedback is free.

| Mistake | Compiler output | Translatable? |
|---|---|---|
| Config for V2 built for V3 | `#error Please select Proffieboard V2 in Tools->Board` | Yes, verbatim |
| Two conflicting prop defines | `#error FETT263_EDIT_SETTINGS_MENU cannot be combined with FETT263_EDIT_MODE_MENU` | Yes, verbatim; also catchable by our prop-definition data before compiling |
| `NUM_BLADES` larger than styles per preset | `cannot convert 'const char*' to 'StyleFactory*'` at the preset-name line of **every** preset, plus `cannot convert 'Preset*' to 'BladeBase*'` at `CONFIGARRAY` | Yes: pattern maps to "preset N has fewer looks than blades". Better: our model validates this before compiling |
| Missing comma after the track | `expected '}' before 'StylePtr'` with a note pointing at the preset's opening `{` line | Yes, the note gives the preset |
| Style typo (`Layerz<`) | `parse error in template argument list` at the config line | Yes, line maps back to the preset/blade because we generate the config |
| Wrong pin name (`blade7Pin`) | **Compiled successfully.** The name exists on V3 | Not a compiler concern: pin validation must be in our hardware profiles |

Because the app generates the config, it can keep a line map (config line → preset, blade, section) and turn each of these into a plain-language message. Everything except the style typo can also be prevented by validating the model before compiling.

## 5. Config-file lessons

- In the ProffieOS `config/` folder, `proffieboard_v1/v2/v3_config.h` are **board pin headers**, not user configs, and `default_v3_config.h` targets TeensySaber V3, not Proffieboard V3. The only stock Proffieboard V3 user config is the 3-blade verification config. Our golden tests need our own V3 corpus.
- Selecting the config means editing `ProffieOS.ino`'s `CONFIG_FILE` line in a private copy of the OS tree. The spike does exactly that; the copy costs a couple of seconds and keeps builds isolated.

## 6. Not exercised

- macOS and Linux bootstrap, udev rules.
- Mass-storage detection with `MOUNT_SD_SETTING` and the `sd` command, and copy speed.
- Electron's Web Serial for the 1200-baud touch (the spike used .NET `SerialPort` from PowerShell; same USB behaviour expected).
- Slower machines, and a V3 board.

## 7. Flash spike on a real Proffieboard V2.2 (2026-09-08)

Board: Proffieboard V2.2 on USB power only, running ProffieOS **v4.7 built July 2020** with the stock 14-preset config, SD card present, no `presets.ini`. A good stand-in for a vendor saber that has never been updated.

| Step | Result |
|---|---|
| Detect running board | `1209:6668` composite device, CDC on COM7 bound to in-box `usbser`, no driver needed |
| Probe over serial (.NET SerialPort, DTR asserted) | `version`, `battery`, `list_presets` answered; `list_named_style` and `id` unknown on v4.7 |
| 1200-baud touch (open at 1200, drop DTR, close) | Board rebooted into `STM32 BOOTLOADER` within a second |
| Fresh machine driver state | Device present, status Error, **problem code 28** (no driver), no service. `dfu-util -l` could list it but reported "Cannot open DFU device" |
| Fix | Owner ran `proffie-dfu-setup.exe` (libwdi) with the board sitting in bootloader mode; afterwards the device showed service `WinUSB`, problem 0, no reboot needed |
| Bootloader memory layout | `@Internal Flash /0x08000000/0128*0002Kg` = 256 KB, which identifies the chip generation (L433) but not V1 vs V2.2 |
| Backup (`dfu-util -U`, 256 KB) | 0.9 s |
| Write (`dfu-util -d 1209:6668,0483:df11 -a 0 -s 0x08000000:leave -D v2-os8.dfu`, 214,800 bytes) | **57.6 s**, 2 KB transfers dictated by the ROM bootloader, then `:leave` reset |
| Re-enumeration | Serial port back well inside the 20 s window |
| Verify | `version` on OS 8.10 printed the `$Id`, **`config/saberbench_v3_os8.h`, `prop: SaberFett263Buttons`, `buttons: 2`, `installed: Sep 7 2026 21:48:57`** |
| Runtime tier on the new firmware | `list_presets` shows all five presets including the argument-reuse ones as `builtin N 1/2`; `battery` works |

Findings:

- **The install pipeline is proven on Windows 11**, including the exact driver failure a new user hits and its fix. Detection must look at the PnP driver service, not at whether `dfu-util -l` lists the device.
- **A DFU write is a minute on its own.** 214 KB at the bootloader's 2 KB transfer size took 58 s, about the same as the compile. Budget roughly two minutes of honest progress for "build and install" on a fast machine.
- **OS 8 `version` gives config identity for free**: config file name, prop, button count and build timestamp. Combined with our own hash header this is enough to re-identify a saber without reading the SD card.
- **`DISABLE_DIAGNOSTIC_COMMANDS` removes commands the app wants.** `list_named_style` and `id` are diagnostic commands and answered "Whut?" on the new firmware. The golden baseline must drop that define (it was added to save flash); measure the cost.
- **A flash backup cannot identify the config.** Strings in the dump show only ProffieOS internals, "Proffieboard" and a font name, confirming the upstream note. Identity has to come from `version` or from files we put on the SD card.
- **The driver installer can run while the board is in bootloader mode**, and binding takes effect immediately. The first-run wizard can therefore be "plug in, we reboot the board, you approve one prompt, done".

Rollback of the original v4.7 firmware is available with `spike/flash.mjs restore` and the backup file in `spike/backups/`.

## 7. Changes fed back into the plan

- Toolchain footprint corrected to 1.6 GB on disk, 357 MB download.
- Compile time recorded: ~1 min on a fast desktop, expect 1 to 3 min on laptops; failures return in under 10 s.
- Build engine: `.dfu` is the artifact; hash cache is the only meaningful cache; one build dir per saber.
- Validation: model-level checks for blade/style count, prop define conflicts and pin names, plus a config line map for compiler errors.
- Flash engine proven; DFU write is about 1 min for a 214 KB image; driver detection via the PnP service.
- Golden baseline: remove `DISABLE_DIAGNOSTIC_COMMANDS` (it hides `list_named_style` and `id`).
- Flash meter calibration points: OS base with edit mode ≈ 195–200 KB; ten OS6-era style instantiations ≈ 227 KB; four current library styles ≈ 216 KB. Model as base + per-distinct-style increment.
